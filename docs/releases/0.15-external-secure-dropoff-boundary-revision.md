## 1. Revision decision

Release 0.15 should explicitly prove the **external Secure Drop-off browser trust boundary** because the base proposal already includes direct large-object upload and the accepted product UX requires an external `Send Us Records` path for files that do not fit ordinary email.

Release 0.15 must therefore prove the real synthetic/no-account browser boundary rather than only a staff-authenticated uploader or infrastructure test harness.

This is a narrow scope addition only.

## 2. Required synthetic external drop-off proof

The Release 0.15 implementation proposal should include synthetic, non-sensitive proof of a public customer-branded `Send Us Records` flow with the following properties.

### 2.1 Safe landing and submission creation

- GET of the public page performs no security-sensitive mutation.
- The server creates an opaque submission context only after an intentional request.
- Submission IDs are high-entropy/opaque and reveal no patient, sender, customer, file, or workflow details.
- Sender-supplied identity is recorded as a **claim / self-reported value**, not as verified identity unless a separate verification event exists.

### 2.2 Short-lived upload authority

- Upload authority is short-lived and scoped to exactly one customer, one submission, and the active product policy.
- The grant permits write only into the quarantine boundary.
- The grant must not provide object listing, object read, arbitrary delete, cross-customer access, or reusable general bucket authority.
- Expired/replayed grants fail closed.
- Browser origin/CORS/request-integrity behavior is explicitly tested.

### 2.3 Opaque object naming

- Object keys are server-created opaque identifiers.
- No PHI/sensitive filenames, patient names, dates of birth, sender names, organization names, email addresses, record types, or other protected context is embedded in the storage key/path.
- Original filename, if retained for controlled display, remains protected application metadata rather than authority or storage routing input.

### 2.4 Server-side enforcement

Do not trust browser-declared values alone.

The server/application boundary must authoritatively enforce the accepted synthetic policy for:

- allowed file count;
- per-file size;
- package/submission total size;
- allowed extension/media/signature policy where implemented;
- multipart part count/size where relevant;
- submission expiration;
- customer/storage ceilings;
- abuse/rate controls.

Production planning target remains **500 MB/file and 1 GB/package**, subject to the cloud proof and later production authorization.

### 2.5 Multipart, interruption, cleanup and retry

Synthetic proof must exercise:

- upload started but abandoned;
- partially completed multipart upload;
- browser/network interruption;
- retry/resume where supported;
- cancellation before final submission;
- cleanup of expired/incomplete upload state and unused objects;
- no stale upload grant continuing beyond policy.

Cleanup behavior must be measurable without placing sensitive information in logs.

### 2.6 Quarantine-only write and release semantics

External browser upload writes only into a non-releasable quarantine state.

Preserve the evidence/state distinction:

**Upload Started != Upload Completed != Submitted/Received != Safety CLEAN != Opened != Patient Confirmed != FILED != Completed != Disposed**

Upload completion must become only a state such as `RECEIVED / SECURITY PROCESSING PENDING`.

Only the separately authoritative scan result can transition content to the reviewed CLEAN/allowed state.

Malware detected, unsupported, encrypted/password-protected where unscannable, extraction/limit exceeded, scan failed, timeout, indeterminate, or other non-CLEAN results remain blocked/fail-closed.

### 2.7 Receipt semantics

The external sender receipt should contain only bounded non-sensitive information appropriate to the synthetic proof, such as:

- opaque reference ID;
- submission date/time/timezone;
- customer support information;
- non-sensitive file count/size summary where appropriate.

The receipt must state clearly that it confirms upload/submission receipt only and does **not** mean:

- security review passed;
- staff opened the records;
- the patient/entity was confirmed;
- records were FILED/transferred;
- the workflow completed;
- temporary content was disposed.

### 2.8 Browser end-to-end acceptance

The proof should include deterministic browser-level tests covering at minimum:

1. customer-branded landing page;
2. sender authorization acknowledgement;
3. required sender/patient-profile fields using synthetic data;
4. file select/drop behavior;
5. planning-target wording shown as planned, not already proven capability;
6. per-file and package progress/state;
7. upload completion -> security-pending state;
8. submission/receipt generation;
9. blocked/unscannable/failure presentation;
10. expiration/replay/abuse boundary cases.

No PHI or real customer records may be used.

## 3. External UX field direction for the synthetic proof

The initial dental profile should model only what is needed for the workflow.

### Sender

Required:

- sender name;
- organization/practice;
- business email;
- acknowledgement: `I am authorized to send these records to [Customer].`

Optional:

- phone.

Do not label the sender verified merely because those values were supplied.

### Patient / record

Default dental profile:

- patient first name — required;
- patient last name — required;
- DOB — required for the synthetic profile unless later evidence changes the product policy;
- patient/chart number — optional if known;
- configurable record type;
- optional attention/department;
- bounded optional notes.

Do not add SSN, insurance details, or other sensitive fields merely for convenience.

### Files

Show:

- drag/drop;
- `Select Files`;
- file count;
- total size;
- per-file progress;
- remove/cancel before final submit;
- allowed-file guidance;
- ZIP/archive guidance;
- warning that password-protected/encrypted archives may be blocked because they cannot be authoritatively inspected.

After bytes upload, wording should be equivalent to:

**Uploaded — security processing pending.**

Do not say safe, clean, accepted for use, filed, or completed before authoritative evidence exists.

## 4. Keep out of Release 0.15

This revision does **not** broaden Release 0.15 into the later communication-edge gate.

Keep out:

- real SES receiving;
- provider redirect/routing proof;
- customer DNS/MX changes;
- DKIM/SPF/DMARC production configuration;
- SES production sending access;
- production no-reply messages;
- email sender verification;
- staff production notifications;
- real Secure Pickup notification/code delivery;
- secure reply;
- PHI/customer production;
- Open Dental/Dentrix/EHR/DMS production writes.

Those remain later separately authorized work.

## 5. Acceptance-evidence addition

A later authorized Release 0.15 implementation return should add explicit evidence for:

- external/no-account browser trust boundary;
- opaque server-created submission/object identifiers;
- short-lived quarantine-only upload grants;
- origin/CORS/request-integrity controls;
- file/count/package/storage/rate enforcement;
- interruption/retry/multipart cleanup;
- sender self-report semantics;
- upload-complete vs received vs CLEAN distinction;
- fail-closed archive/unscannable behavior;
- synthetic external receipt semantics;
- full external browser end-to-end proof.

## 6. Stop conditions added by this revision

Stop and return to Product Orchestrator if:

- the external uploader requires broad/read/list/delete S3 authority;
- object paths would expose sensitive metadata;
- a short-lived upload grant cannot be constrained tightly enough;
- browser CORS/origin controls require an unsafe relaxation;
- package limits can be bypassed by multipart/concurrent upload behavior;
- upload completion would have to be treated as CLEAN/accepted;
- unsupported/unscannable archives cannot be kept fail-closed;
- external browser proof requires PHI or a real customer before the synthetic gate is accepted.

## 7. Non-authorization

This document records only the revised proposed Release 0.15 boundary. It does not authorize implementation. Product/Portfolio must separately approve any Release 0.15 implementation, AWS spend cap, deployment target, and exact execution handoff.
