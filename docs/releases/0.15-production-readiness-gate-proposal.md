## 1. Proposed release

**Release 0.15 — Customer-Owned AWS Foundation & Protected-Object Production-Readiness Proof**

Release 0.15 should prove the hardest common infrastructure/security foundation once, using synthetic/non-sensitive data only, before provider-specific mail or downstream integrations are allowed to expand the scope.

The release should answer one question:

> Can the accepted Secure Exchange application/security model be deployed repeatably into an isolated customer-owned-style AWS environment with deterministic GitHub delivery, bounded identity/configuration, protected large-object transfer, authoritative fail-closed malware handling, conservative evidence/logging, rollback and offboarding — without customer-specific source code?

A positive result is still **not production authorization**. It becomes evidence for the next Product/Portfolio gate.

## 2. Why Release 0.15 is bounded here

The commercial gate requires eventual proof of inbound mail routing, SES notifications, Secure Pickup, and downstream adapters, but combining all of those with first-time AWS/IaC/identity/object-security work in one release would create an unnecessarily large validation slice.

Release 0.15 therefore proves the common AWS and protected-content substrate first. Later separately authorized slices can layer:

1. provider mail-routing / SES ingress and PHI-safe staff notifications;
2. outbound SES no-reply notification telemetry + Secure Pickup;
3. downstream Open Dental/manual workflow production boundary and later adapters.

This sequencing preserves the accepted **problem -> service -> standard method -> automation -> reusable product** discipline.

## 3. Proposed Release 0.15 scope

### 3.1 Infrastructure as code

Create a parameterized, repeatable AWS reference deployment behind existing provider-neutral application contracts.

Candidate components must be justified individually and should remain serverless/low-cost:

- S3 protected object/quarantine boundary;
- DynamoDB state where the accepted repository model requires it;
- Lambda/API execution boundary where required;
- customer-owned KMS key if the security proof retains it;
- Cognito or another approved reference staff-identity adapter;
- CloudWatch/EventBridge/CloudTrail only to the minimum level required for operations/evidence;
- Systems Manager standard parameters or another approved configuration/secret boundary;
- optional frontend delivery component only if needed to prove the real browser boundary.

Do not add EC2, RDS, NAT Gateway, load balancers, Kubernetes, OpenSearch, paid monitoring SaaS, paid AWS support, multi-region replication, or other recurring infrastructure without a specific gate return justifying it.

### 3.2 GitHub -> AWS deployment

Prove deterministic deployment/update from the authoritative GitHub repository using short-lived OIDC credentials.

Required properties:

- no permanent AWS access key in GitHub;
- deployment trust restricted to the intended LDW repository/ref/environment as tightly as the chosen AWS/GitHub mechanism supports;
- least-privilege deployment role;
- changeset/plan visibility before consequential promotion where practical;
- reproducible deploy from a known commit/release;
- synthetic post-deploy smoke test;
- documented rollback to the prior known-good application/infrastructure version;
- no customer secret or sensitive config written to public workflow logs.

### 3.3 Customer bootstrap/configuration contract

Define and prove the minimum customer-owned account bootstrap path without taking over billing, root, MFA or recovery authority.

The proof should model:

- customer account ID / target region;
- scoped LDW deployment role bootstrap;
- first administrator;
- organization name/logo/accent/profile;
- allowed file policy;
- retention policy within approved bounds;
- notification destinations as non-sensitive configuration;
- downstream profile selector;
- staff security policy such as session bounds/access hours where implemented.

The mature target remains **configuration, not customer-specific code**.

A future setup wizard may own these values; Release 0.15 may use a bounded synthetic configuration surface if a full wizard would materially enlarge the proof.

### 3.4 Staff identity/session/recovery proof

Prove the reference production identity/session boundary using synthetic users.

At minimum evaluate and test:

- MFA-required staff baseline;
- bounded concurrent sessions;
- idle and absolute session limits;
- logout/revocation;
- disabled-user denial;
- last-login visibility;
- failed-login throttling/lock behavior;
- recovery/break-glass ownership without LDW retaining customer recovery secrets;
- optional business/access-hours policy as configuration, not hard-coded product behavior;
- authorized-use notice/acknowledgement evidence if included in the release.

Do not claim HIPAA compliance from these controls alone.

### 3.5 Protected object quarantine and release authority

All inbound/outbound protected files must first exist in a non-releasable quarantine state.

The application remains authoritative for whether content can be released. Object presence, upload completion, provider metadata or browser possession is not release authority.

Required state distinction should include at least:

- upload pending/incomplete;
- quarantined;
- scanning;
- CLEAN/allowed;
- malware detected;
- unsupported/unscannable;
- scan failed/indeterminate;
- disposed.

Only the explicitly reviewed **CLEAN/allowed** state may permit protected read/download/transfer behavior.

### 3.6 Type/signature/archive hardening

Do not trust browser MIME type or filename extension alone.

Prove a bounded file policy using synthetic fixtures and server-side inspection appropriate to the accepted file types.

Archive/compound handling must test at minimum:

- ordinary ZIP;
- nested ZIP;
- multiple nested levels within supported policy;
- password-protected/encrypted archive;
- malformed archive;
- high compression-ratio/archive-bomb style safe fixture;
- excessive entry-count safe fixture where practical;
- unsupported compound format;
- malware-test fixture such as EICAR only where the approved scanner/test method permits it;
- scanner/provider error/timeout/indeterminate event.

GuardDuty Malware Protection for S3 is the current reference scanner, subject to exact live documentation/service eligibility and hands-on proof at implementation time.

If GuardDuty returns malware, failed, unsupported, unscannable, over-limit or indeterminate state, Secure Exchange must fail closed.

No test fixture may contain real malware, PHI or customer data.

### 3.7 Large-file transfer proof

Production planning target remains:

- **500 MB maximum individual file**;
- **1 GB maximum package/submission**.

Release 0.15 should prove the safe transfer architecture with synthetic generated content, including:

- direct protected upload rather than proxying huge binaries through the API body;
- authorization before upload commitment;
- incomplete/multipart upload cleanup;
- retry/resume behavior where supported;
- package/file size enforcement server-side;
- per-customer/storage abuse controls;
- object naming that does not expose sensitive metadata;
- direct protected download mechanism that does not create an unreasonably long-lived bearer URL;
- download interruption/retry behavior;
- authoritative Downloaded evidence semantics distinct from Opened;
- cleanup/disposition behavior after the synthetic lifecycle completes.

A smaller synthetic fixture may be used for most automated CI tests; at least one bounded cloud proof should exercise the actual 500 MB/file and 1 GB/package planning boundaries if the later implementation authorization permits the small associated AWS cost.

### 3.8 PHI-safe logging, alerts and evidence

Prove that the AWS reference can be operated without putting protected content into ordinary logs/metrics/alerts.

Required direction:

- structured identifiers rather than sensitive filenames/patient names in logs;
- count/status/error-code telemetry only where sufficient;
- no request/response body logging for protected content;
- no secrets/tokens/bootstrap proofs in logs;
- non-sensitive operational alerts only;
- evidence facts remain application-owned and semantically distinct;
- explicit log retention/configuration review;
- incident diagnostics designed around synthetic/minimized reproduction before PHI access.

### 3.9 Disposition, backup/recovery and restore invalidation

Prove the distinction between access expiry and actual deletion.

Required behaviors:

- application-controlled disposition is authoritative;
- provider lifecycle/TTL may be a cleanup backstop only;
- disposed protected objects are not silently resurrected into active authority by ordinary state restore;
- backup/recovery design is documented before production and minimizes unnecessary protected-content duplication;
- rollback of application/infrastructure does not roll back authorization/security epochs in a way that revives revoked/expired access;
- customer offboarding/export/handoff procedure is defined for the customer-owned model.

### 3.10 Cost guardrails

The implementation gate must include a pre-deploy cost estimate and post-proof actual-cost reconciliation.

Target for a synthetic proof should remain as close to `$0` as practical and should require explicit Product/Portfolio approval before any non-trivial paid resource is created.

Production architecture must preserve the current small-practice planning objective rather than introduce an avoidable fixed monthly floor beyond justified security components.

## 4. Explicit Release 0.15 non-scope

Do **not** include in this release unless a later gate explicitly expands it:

- PHI/customer data;
- production customer deployment;
- customer DNS/MX/SPF/DKIM/DMARC changes;
- real records forwarding/routing;
- SES production sending access;
- real external no-reply notifications;
- staff production notifications;
- real Secure Pickup emails;
- Hushmail/Zoho/Microsoft/Google production integration;
- Open Dental API writes or direct database writes;
- Dentrix/EHR/EMR/legal DMS adapters;
- OCR/AI extraction;
- multi-tenant LDW SaaS;
- LDW-owned PHI hosting;
- public pricing;
- public compliance/certification claims.

## 5. Future Gate 0.16 proposal boundary — mail ingress + notifications + pickup

If Release 0.15 proves the common foundation, the next candidate should validate the communication edge using synthetic data:

- SES receiving boundary and current email-size limit;
- supported-provider redirect/routing recipes;
- records-only subdomain path for customers retaining free ordinary mail;
- `no-reply@customer-domain` or dedicated notification-subdomain sending identity;
- SPF/DKIM/DMARC configuration/rollback runbook;
- SES sandbox-to-production-access prerequisites;
- bounce/complaint/delay/delivery event processing;
- non-sensitive staff alerts for new/Needs Attention/expiry/failure events;
- non-sensitive external Secure Pickup notification;
- Release 0.12 bootstrap/session boundary reuse;
- recipient-specific AccessGrant, expiry, revoke/reissue and download evidence;
- secure external reply/upload only if separately scoped and safety-gated.

That future gate must still use synthetic/non-sensitive data before any PHI authorization.

## 6. Future downstream gate

Open Dental remains the first concrete downstream profile.

The initial production candidate should preserve manual filing + explicit FILED confirmation unless a later business/technical gate proves API automation is worth its licensing/integration/support cost.

Later adapters such as Dentrix, other EHR/EMR, legal DMS/case systems or generic downstream APIs remain separate opportunities and must not turn the core product into a vertical-specific fork.

## 7. Acceptance evidence required from Release 0.15 implementation

A later authorized implementation return should include, at minimum:

1. exact live base/head/tree and changed files;
2. exact AWS services/resources created and why each is necessary;
3. exact HIPAA-eligible-service/BAA evidence current at implementation time, while clearly stating the proof uses no PHI;
4. IAM/OIDC trust and least-privilege review;
5. deterministic IaC deploy/update/rollback evidence;
6. synthetic identity/session/recovery test evidence;
7. protected-object state-machine and authorization tests;
8. archive/nested/unscannable/failure test matrix;
9. 500 MB/file and 1 GB/package boundary test evidence if authorized;
10. incomplete upload, retry, abuse and cleanup proof;
11. PHI-safe log/alert review;
12. disposition/restore/offboarding proof;
13. full unit/integration/architecture/browser/security/dependency/secret/build validation;
14. actual proof cost versus estimate;
15. explicit remaining gaps and stop/go recommendation.

## 8. Stop conditions

Stop and return to the Product Orchestrator rather than improvising if:

- a required AWS service is not HIPAA-eligible for the intended future use;
- the proposed BAA/service responsibility chain is unclear;
- the scanner cannot provide a fail-closed authoritative result for the required archive/file policy;
- large-file transfer requires exposing long-lived reusable bearer credentials;
- customer-specific source forks appear necessary for ordinary deployments;
- expected small-practice recurring cost materially exceeds the accepted planning model without demonstrated value;
- identity/recovery requires LDW custody of customer owner passwords/MFA/recovery secrets;
- production proof would require PHI or a real customer before the synthetic gate is accepted;
- a change would require customer DNS/mail/billing/recovery/production action without the required approval.

## 9. Proposed authorization request after proposal review

If Product/Portfolio accepts this proposal, authorize **Release 0.15 only** as a synthetic/non-PHI production-readiness proof with a separately stated AWS spend cap and exact deployment target.

Do not authorize Release 0.16 communication-edge work, PHI, customer production, customer BAAs, DNS/mail changes, or downstream writes by accepting Release 0.15.

## 10. Current commercial dependency

Broad production implementation remains gated on customer demand evidence.

The accepted business sequence is:

**revised proposal + synthetic UX mock -> qualified practice review -> paid design-partner / comparably strong intent signal -> Product/Portfolio production authorization.**

If the customer need is only secure healthcare email + simple secure forms + manual filing, recommend/configure a maintained solution such as Hushmail rather than using this release proposal as a reason to force Secure Exchange.
