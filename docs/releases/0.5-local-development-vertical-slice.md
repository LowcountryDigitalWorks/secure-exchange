# Release 0.5 — Local Development Vertical Slice

## Purpose

Release 0.5 wires the existing provider-neutral workflow and conversation services into the first usable browser-driven Secure Exchange development slice.

The synthetic flow is:

`external development form -> accountless synthetic initiation -> synthetic staff queue -> authoritative conversation open -> chronological messages -> authorized staff reply`

This is a **Synthetic Development Demo** only. It is not production authentication, a production public portal, a regulated deployment, or production infrastructure. Use synthetic data only; do not enter real customer, patient, client, confidential, regulated, or PHI data.

## Development enablement gate

The functional browser demo is disabled by default. `createApp()` without a development runtime exposes the existing engineering shell and `/health`, while `/demo/*` returns not found.

Local process enablement is explicit:

```sh
SECURE_EXCHANGE_SYNTHETIC_DEMO=enabled npm run dev
```

or, after building:

```sh
SECURE_EXCHANGE_SYNTHETIC_DEMO=enabled npm start
```

Playwright enables the same flag only for its isolated local test server.

## Application composition

`createApp({ demo })` is the thin Hono delivery adapter. The injected development runtime owns:

- the existing `ConversationService`;
- the existing `WorkflowService`;
- the existing in-memory `WorkflowStore` adapter;
- one synthetic deployment and queue;
- one server-held synthetic STAFF context and authorization record;
- an injectable opaque ID generator;
- an injectable clock.

HTTP handlers parse bounded delivery input, enforce development delivery controls, generate trusted IDs where required, and delegate business behavior to the application services. They do not reimplement queue, thread, authorization, lifecycle, message, or transaction rules.

## Synthetic configuration

The local runtime seeds one development deployment, one active queue with bounded `GENERAL` and `RECORDS` routing choices, and one active STAFF authorization with the minimum permissions needed for this slice:

- `QUEUE_LIST`;
- `THREAD_OPEN`;
- `THREAD_REPLY`;
- `THREAD_TRANSITION` for the optional explicit Start work action.

There is no username/password login. Browser input cannot choose actor IDs, permissions, deployment IDs, queue grants, or internal queue authority identifiers.

## Opaque authoritative identifiers

The browser form accepts only a permitted routing category and bounded synthetic message text. Authoritative identifiers are generated server-side behind the provider-neutral `OpaqueIdGenerator` boundary.

The local adapter uses Web Crypto `randomUUID()` for:

- external participant references;
- thread IDs;
- message IDs;
- audit-event IDs.

Browser-supplied values for those identifiers are ignored and never become authorization or audit identity. IDs are not derived from message content, routing category, sender/contact data, or network address. This local adapter establishes the trust boundary; it is not the final production identifier design.

## Reply lifecycle rule

Staff reply eligibility is a provider-neutral business rule, not a UI rule.

Replies are permitted only while a thread is:

- `NEW`;
- `IN_PROGRESS`;
- `AWAITING_EXTERNAL`;
- `AWAITING_STAFF`.

Replies fail closed for:

- `COMPLETED`;
- `EXPIRED`;
- `DISPOSED`.

A successful reply does not automatically change lifecycle state. The established evidence separation remains authoritative:

**Opened != Downloaded != Transferred/Filed != Completed.**

## Development routes

All routes below are development delivery adapters and are not a stable production public API.

| Method | Route | Behavior |
|---|---|---|
| `GET` | `/demo` | Synthetic Development Demo landing page |
| `GET` | `/demo/external` | Minimal external synthetic initiation form |
| `POST` | `/demo/external` | Server-generated-ID initiation through `ConversationService` |
| `GET` | `/demo/external/confirmation` | Development confirmation only; grants no external conversation access |
| `GET` | `/demo/staff/queue` | Metadata-only queue view from `listQueueCandidates()` |
| `POST` | `/demo/staff/threads/:threadId/open` | Explicit Opened evidence through `openStaffConversation()` then redirect |
| `GET` | `/demo/staff/threads/:threadId` | Authorized non-mutating conversation read |
| `POST` | `/demo/staff/threads/:threadId/reply` | Version-protected authorized staff reply |
| `POST` | `/demo/staff/threads/:threadId/start` | Optional explicit `NEW -> IN_PROGRESS` action through `WorkflowService` |

No GET route mutates application state. Mutations use POST/Redirect/GET.

## Queue and conversation safety

The staff queue is backed by `ConversationService.listQueueCandidates()` and renders bounded candidate metadata only. Message bodies are not projected into the queue.

Opening a conversation is an explicit POST that records the existing distinct Opened evidence before redirecting to the conversation page. The redirected GET performs a fresh authoritative `THREAD_OPEN` check through `readStaffConversation()` and renders chronological immutable messages.

Queue appearance and possession of an opaque thread reference are never authorization proof.

## Browser output and request safety

Server-rendered configuration and message text is escaped for HTML output. Script- and markup-shaped synthetic messages render as text rather than executable markup. No client-side JavaScript is introduced.

Development pages use:

- `Content-Security-Policy` with `default-src 'none'`, same-origin styles/connections, `base-uri 'none'`, `frame-ancestors 'none'`, and only `form-action 'self'` when the demo is enabled;
- `Referrer-Policy: no-referrer`;
- `X-Content-Type-Options: nosniff`;
- `X-Frame-Options: DENY`;
- `Cache-Control: no-store` for `/demo/*`.

Mutation requests use a small same-origin boundary. Browser requests with Fetch Metadata are accepted only when `Sec-Fetch-Site` is `same-origin`. Non-browser/in-memory callers without Fetch Metadata must satisfy the strict Origin/host/request-URL fallback. Missing and cross-site signals fail closed.

## Error handling

Domain and application failures are mapped to bounded development responses. The browser does not receive stack traces, authorization mappings, staff permissions, cross-deployment existence details, or message content in errors.

Stale expected-version or reply-state failures return a bounded conflict response. Authorization/not-found behavior remains conservative.

## Persistence

The existing in-memory adapter is reused. State may persist for the life of the local process and may reset at restart.

No DynamoDB, SQLite, PostgreSQL, browser localStorage database, production database, or reset endpoint is introduced. The in-memory representation remains development/test infrastructure rather than a production persistence contract.

## Explicit non-goals

Release 0.5 does not introduce production authentication, username/password login, Cognito, production sessions, real customer identity, public Internet deployment, Cloudflare/AWS production infrastructure, customer data, PHI, attachments, upload/download, object storage, malware scanning, `ATTACHMENT_DOWNLOADED` browser behavior, AccessGrant, external secure retrieval/reply, email notifications, SES, S3, DynamoDB, GuardDuty, KMS, API Gateway/Lambda deployment, infrastructure as code, paid services, analytics, or a large frontend framework.
