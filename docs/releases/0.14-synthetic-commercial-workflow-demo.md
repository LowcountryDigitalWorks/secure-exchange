# Release 0.14 — Synthetic Provider-Augmented Commercial Workflow Demo

## Purpose

Release 0.14 provides the smallest synthetic/local commercial workflow demonstration needed to validate Secure Exchange with a dental-practice workflow while preserving the generic Secure Exchange core. It demonstrates:

synthetic external records intake -> existing attachment safety path -> staff queue -> synthetic patient resolution -> read-only attachment preview -> proposed filing mapping -> human correction/confirmation -> deterministic synthetic downstream result -> explicit staff FILED confirmation -> completion -> disposition.

This release is a workflow-validation and commercial-demo slice only. It is not a production deployment, real mail-provider integration, real Open Dental integration, provider-confirmed filing implementation, HIPAA-readiness claim, or customer-data path.

## Activation

The commercial routes are disabled by default and are registered only when both development gates are enabled:

```sh
SECURE_EXCHANGE_SYNTHETIC_DEMO=enabled \
DEMO_COMMERCIAL_WORKFLOW_ENABLED=enabled \
npm run dev
```

The bounded namespace is `/demo/commercial/*`. The existing Release 0.9–0.11 `DEMO_EXTERNAL_RETRIEVAL_ENABLED` gate remains independent.

Every commercial page is prominently labeled **SYNTHETIC DEVELOPMENT DEMO** and warns that no real patient, customer, confidential, regulated, or PHI information may be entered.

## Generic Secure Exchange boundary

Release 0.14 does not put dental-specific data into generic `Thread`, `Message`, `Attachment`, domain, or application models.

The only generic application extension is authorized staff attachment candidate/preview resolution. It validates current deployment, thread, STAFF authorization, queue scope, `ATTACHMENT_READ`, message/attachment ownership, exactly-`CLEAN` safety state, protected-content existence, and byte-length integrity.

Preview and download reuse the same authoritative attachment-resolution checks. Preview is read-only and creates no workflow audit mutation. Manual download continues through the existing retrieval path and creates the existing `ATTACHMENT_DOWNLOADED` evidence only after successful retrieval.

Architecture regression tests reject dental-specific identifiers in `src/domain` and `src/application` and reject provider SDK imports in the bounded commercial demo slice.

## Synthetic intake and attachment safety

The commercial intake accepts one to four synthetic attachments, each no larger than 2 MiB, limited to:

- `application/pdf` / `.pdf` / `DOCUMENT`;
- `image/png` / `.png` / `IMAGE`;
- `image/jpeg` / `.jpg` or `.jpeg` / `IMAGE`;
- `text/plain` / `.txt` / `TEXT`.

All files use the existing `AttachmentService` and protected-content store. New content is first published as `QUARANTINED`; the demo then performs an explicitly synthetic trusted scan-result step through the existing `recordScanResult(... CLEAN ...)` path. No file is published directly as `CLEAN`.

No SVG, HTML, Office parsing, archives, OCR, AI classification, image transformation, or universal rendering is added.

## Preview and manual download

CLEAN PNG/JPEG content may be displayed through a same-origin image preview. CLEAN PDFs are served as a dedicated top-level browser-native preview response rather than embedded by weakening anti-framing policy. Supported non-previewable types use bounded metadata plus the explicit manual-download fallback.

Preview responses use the authoritative normalized media type and conservative controls including no-store/private caching, `nosniff`, `no-referrer`, and same-origin resource policy. Global anti-framing controls remain intact.

Preview GETs do not create `ATTACHMENT_DOWNLOADED`, TransferAttestation, completion, or lifecycle evidence. Manual download is a same-origin POST and retains the existing successful-download audit behavior.

The synthetic preview UX is not a production regulated-audit contract; that boundary must be reviewed again before a regulated deployment.

## Synthetic patient workflow adapter

Dental-specific state is held only by the local in-memory `SyntheticCommercialWorkflow` adapter. It resets with the process and makes no network or provider call.

The fixed synthetic patient fixtures support three explicit staff paths:

1. verify a known synthetic patient number against the fixture allowlist, then explicitly confirm the returned fixture;
2. search fixed fixtures by bounded name + DOB, then explicitly select a result;
3. select `Patient not found / unresolved`, which blocks downstream filing.

There is no patient-creation path.

Optional intake name/DOB values are shown only as **SENDER-SUPPLIED MATCHING EVIDENCE**. They assist the synthetic search workflow and are never represented as downstream demographic updates.

## Filing mapping and correction

Each synthetic attachment receives a demo-only proposed filing mapping. Destination/category and classification options come from fixed server-side allowlists. Staff may change only those bounded values through normal server-rendered forms.

The filing preview explicitly distinguishes **WILL CHANGE** from **WILL NOT CHANGE**. Downstream demographics, sender-supplied DOB, and immutable uploaded source bytes are in the `WILL NOT CHANGE` boundary.

No drag/drop, mirroring, flipping, rotation, image editing, derivative generation, or transformed filing copy is implemented.

## Synthetic downstream result and FILED evidence

The downstream adapter is deterministic and local-only. Staff may deliberately demonstrate:

- **SIMULATED / SYNTHETIC FAILURE**;
- retry;
- **SIMULATED / SYNTHETIC SUCCESS**;
- manual-download fallback.

A simulated success is only demo-adapter state and never creates a TransferAttestation automatically.

After simulated success, the separate `Confirm simulated filing` staff action invokes the existing `WorkflowService.appendTransferAttestation()` with outcome `FILED` and the bounded generic destination category `SYNTHETIC_PATIENT_RECORD`.

The existing TransferAttestation remains thread-level authenticated staff evidence. It is not provider-confirmed Open Dental evidence and does not preserve every per-attachment demo mapping field.

The demo reserves filing confirmation before invoking the workflow service so duplicate/replayed confirmation cannot silently append uncontrolled duplicate qualifying evidence in the local process.

## Completion and disposition

The synthetic development composition configures the existing completion policy with:

- `requiresTransferAttestation: true`;
- qualifying outcome `FILED` only;
- allowed destination `SYNTHETIC_PATIENT_RECORD` only.

A simulation flag does not satisfy completion. Completion remains an explicit `WorkflowService.completeThread()` operation and does not itself dispose the exchange. Disposition remains a separate authorized lifecycle transition.

The evidence invariant remains:

**Opened != Downloaded != Transferred/Filed != Completed != Disposed.**

## Diagnostics and synthetic notification

Diagnostics are local in-memory aggregate counters with a fixed key allowlist only:

- `patient_number_verified`;
- `patient_search_selected`;
- `patient_not_found_selected`;
- `proposed_category_corrected`;
- `proposed_classification_corrected`;
- `filing_preview_changed`;
- `synthetic_transfer_failed`;
- `synthetic_transfer_retried`;
- `manual_download_fallback_used`.

There is no `new_patient_created` counter or arbitrary diagnostic payload. Diagnostic serialization contains only counter names and integer counts; it contains no patient name, DOB, patient identifier, filename, message body, bytes, credential, token, bearer, verifier, or provider secret. No telemetry leaves the process.

The only synthetic provider-notification representation is the fixed non-sensitive local message:

> A secure exchange item is available.

No email, SMTP, provider API, or network notification is sent.

## Security and privacy boundary

All authoritative commercial mutations are POST-only and retain same-origin checks. GET routes are read-only. CSP remains restrictive; the commercial gate adds only same-origin image loading required for the synthetic PNG/JPEG preview. No third-party scripts, fonts, trackers, analytics, or client libraries are introduced.

Release 0.13 bootstrap/session behavior and the existing raw AccessGrant development path are preserved. Release 0.14 does not add a new public/browser transport for the 0.13 session core and does not weaken AccessGrant/session authorization.

Synthetic fixtures only. No real PHI, patient records, customer information, production identifiers, credentials, OAuth tokens, API keys, or production infrastructure configuration belong in this repository, demo, logs, screenshots, issues, pull requests, or test data.
