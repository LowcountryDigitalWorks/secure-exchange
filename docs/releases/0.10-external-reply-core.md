# Release 0.10 — External Reply Core Prototype

## Scope

Release 0.10 adds provider-neutral AccessGrant-authorized external reply in the domain/application layer with synthetic/local persistence only. It adds no browser reply form/API, email delivery, external attachment upload, production authentication, cloud infrastructure, customer data, PHI, analytics, or paid service.

## Explicit AccessGrant authority

The AccessGrant operation vocabulary is exactly `THREAD_READ`, `ATTACHMENT_READ`, and `THREAD_REPLY`. Operations are independent; no wildcard exists and existing grants do not silently gain reply authority. The current AccessGrant policy must explicitly permit every requested operation.

If issuance includes `THREAD_REPLY`, the current authoritative thread must also be reply-eligible. Reply authority is never silently removed from an otherwise requested mixed grant.

## Reply lifecycle

External reply is allowed only in `NEW`, `IN_PROGRESS`, `AWAITING_EXTERNAL`, and `AWAITING_STAFF`. It is denied in `COMPLETED`, `EXPIRED`, and `DISPOSED`. This rule is separate from broad external read eligibility: a valid `THREAD_READ` grant may read `COMPLETED`, while `THREAD_REPLY` cannot reply there.

A reply never automatically transitions lifecycle. In particular, `AWAITING_EXTERNAL` remains `AWAITING_EXTERNAL` unless an explicit workflow action changes it.

## Application and actor boundary

`AccessGrantService.replyExternalConversation()` accepts only deployment/thread/grant selectors, bearer secret, and bounded plain-text body. It reuses the existing AccessGrant verifier/scope/revocation/expiry/current-thread validation with explicit `THREAD_REPLY`, then applies the stricter reply lifecycle rule.

The immutable reply message is `EXTERNAL_TO_STAFF`. Actor attribution comes only from the authoritative grant's opaque `externalParticipantRef`. Message ID, audit ID, actor kind, and timestamp are generated or supplied through trusted server-side application boundaries, not by the external caller.

## Activity, attention, and atomicity

New external activity advances `updatedAt`, `lastActivityAt`, and `attentionAt` to the reply timestamp while preserving lifecycle. `attentionAt` means staff-facing attention is warranted by newer external activity; it does not mean every staff user is unread and it is not a read receipt.

The new message, expected-version thread activity/attention update, and minimized `MESSAGE_APPENDED` audit event commit atomically through `WorkflowStore`. Stale or failed commits publish none of those reply artifacts.

## Audit minimization

Successful reply evidence may contain opaque event/deployment/thread/external actor/message/grant identifiers, actor kind `EXTERNAL`, timestamp, and bounded success outcome. It does not contain the message body, bearer secret, verifier, unrestricted external contact information, browser cookie/request body, TransferAttestation, or completion event.

## Browser boundary

Release 0.9 browser retrieval remains unchanged. Release 0.10 adds no `/reply` route, reply form, reply button, reply API, or client JavaScript. Browser reply delivery, capability-cookie use, same-origin controls, abuse controls, and production bootstrap remain Release 0.11/later decisions.

## Dependencies and cost

No runtime or development dependency is added or changed. Package metadata advances to `0.10.0`. New recurring cost is **$0**.

## Validation gate

Merge readiness requires the permanent read-only `CI / validate` workflow on the exact release head and the separate protected-main pull-request-context `validate` check. Temporary release-finalization workflows are not part of the candidate tree.
