# Release 0.4 — Conversation & Queue Core Prototype

## Purpose

Release 0.4 implements provider-neutral conversation and queue behavior that later HTTP/browser delivery can call without moving business rules into routes. It is a synthetic/local prototype only.

## Implemented domain model

### Queue

A queue is deployment-bound non-sensitive configuration with:

- opaque queue identifier;
- deployment identifier;
- active/inactive state;
- bounded display label;
- one or more bounded permitted routing categories.

External initiation fails closed if the queue is absent in the requested deployment, inactive, or does not permit the requested routing category.

### Thread reconciliation

The executable `Thread` now includes the approved conversation/work-list metadata:

- deployment ID;
- thread ID;
- queue ID;
- routing category;
- lifecycle state;
- created and updated timestamps;
- last-activity timestamp;
- optional attention timestamp;
- existing completion, disposition, and optimistic-version semantics.

Conversation activity can advance `updatedAt`, `lastActivityAt`, and the optimistic version without changing lifecycle state. Attention metadata is not defined as per-user unread state and is not silently cleared by an open or reply.

### Message

A message is immutable and contains:

- opaque message ID;
- deployment and thread IDs;
- direction: `EXTERNAL_TO_STAFF` or `STAFF_TO_EXTERNAL`;
- direction-appropriate actor/reference;
- created timestamp;
- bounded body representation.

The Release 0.4 body representation is `{ kind: "PLAIN_TEXT", text }`, bounded to 8,000 code units, normalized to LF line endings, non-empty after trimming, and rejected if it contains disallowed control characters. This simple representation keeps the provider-neutral model explicit for the local synthetic prototype. It is not an object-storage, encryption, DynamoDB, or production message-storage contract.

Messages are never edited in place. Corrections require a later explicit mechanism or a new message.

## Application boundaries

### External initiation

`ConversationService.initiateExternalExchange` is an application/domain capability only. It does not expose a public HTTP endpoint.

It validates the deployment-bound queue and routing category, bounded external participant reference, and bounded initial message. It then atomically creates:

- one `NEW` thread at version 1;
- one immutable `EXTERNAL_TO_STAFF` message;
- minimized `THREAD_CREATED` and `MESSAGE_APPENDED` audit events.

The external participant reference is not inserted into staff `ActorAuthorization` merely for convenience.

### Queue candidate view

`ConversationService.listQueueCandidates` requires current deployment, active normalized actor authorization, queue scope, and `QUEUE_LIST` permission.

Rows contain only bounded work-list metadata: thread/queue ID, routing category, lifecycle state, and created/updated/activity/attention timestamps. They never contain message bodies.

**Queue membership is candidate information, not authorization proof.** A candidate result cannot authorize content access or mutation.

### Staff conversation open/read

`ConversationService.openStaffConversation` validates current deployment, authoritative thread ownership, active normalized actor, queue scope, and `THREAD_OPEN` before loading messages. Messages are returned chronologically after authorization. The same operation records distinct `THREAD_OPENED` evidence.

Opening does not imply attachment download, TransferAttestation, or completion.

### Staff reply

`ConversationService.replyToConversation` requires authoritative thread authorization, `THREAD_REPLY`, and a normalized `STAFF` actor. It appends an immutable `STAFF_TO_EXTERNAL` message and atomically updates thread activity/version plus a minimized `MESSAGE_APPENDED` audit event.

Reply does not infer a lifecycle transition, download, TransferAttestation, or completion.

## Authorization vocabulary

Release 0.4 adds only:

- `QUEUE_LIST`;
- `THREAD_REPLY`.

It reuses `THREAD_OPEN` for authoritative conversation open/read. Existing lifecycle, disposition, transfer-attestation, completion, and download-evidence permissions remain unchanged.

External initiation uses its own narrow unauthenticated application boundary and does not masquerade as staff authorization.

## Audit minimization

New audit event types:

- `THREAD_CREATED`;
- `MESSAGE_APPENDED`.

Existing `THREAD_OPENED` is reused for authorized staff conversation opening.

Audit events may contain opaque target identifiers and normalized actor/reference data. They do not copy message bodies, contact-message content, attachment content, credentials, grants, or unrestricted metadata.

## Atomicity and local persistence

The in-memory adapter now supports queues, messages, thread creation, and thread activity updates. Its copy-on-write commit path stages all affected records and publishes them only if the whole synthetic transaction succeeds.

External initiation therefore commits thread + initial message + audit together. Staff reply commits message + thread activity/version + audit together. Injected transaction failures prove rollback.

The in-memory maps, arrays, resource-key helper, chronological sort, and copy-on-write mechanism are test/development infrastructure. They are not the DynamoDB schema or production transaction contract.

## Unread/new semantics

Release 0.4 deliberately does not invent per-user unread/read-position state.

- lifecycle `NEW` describes workflow state;
- `THREAD_OPENED` is workflow evidence;
- `lastActivityAt` is thread activity metadata;
- `attentionAt` is a bounded work-list attention anchor.

None is defined as a universal per-user unread flag. A durable read-position/read-receipt model requires a separate decision if later UX needs per-user unread counts.

## Attachment/download-evidence follow-up

Release 0.4 implements no attachment retrieval.

Future production `ATTACHMENT_DOWNLOADED` evidence must be emitted only by the authoritative successful retrieval path after validating, at minimum:

- deployment and thread ownership;
- attachment ownership;
- current actor/access authority;
- retrievable lifecycle state;
- release-eligible malware state such as `CLEAN`.

The existing standalone synthetic evidence method must not become a public/browser download action.

## Deliberate non-goals

Release 0.4 does not implement:

- production public submission endpoint;
- finished public submission UI;
- production staff UI;
- external secure retrieval or external reply;
- AccessGrant tokens or secrets;
- attachment upload/download;
- object storage;
- malware scanning;
- email notifications;
- Cognito, SES, S3, DynamoDB, GuardDuty, KMS, API Gateway, or Lambda deployment;
- AWS SDK adapters;
- infrastructure as code;
- production authentication/session management;
- production secrets/configuration;
- rate-limiting/bot implementation;
- customer integrations;
- customer data or PHI;
- paid services;
- a large frontend framework.

## Cost

Release 0.4 introduces no production resources or paid service. New recurring cost is $0.
