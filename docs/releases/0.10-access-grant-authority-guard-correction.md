# Release 0.10 — AccessGrant Authority Guard Correction

## Purpose

This record documents the blocking orchestrator correction applied to Release 0.10 — External Reply Core Prototype. The correction closes the external-reply AccessGrant concurrency and expiry-boundary TOCTOU without changing the approved Release 0.10 product scope.

## Provider-neutral transaction guard

`WorkflowMutation` now supports a read-only `AccessGrantAuthorityGuard` with:

- `deploymentId`
- `threadId`
- `grantId`
- `expectedVersion`
- `requiredOperation`
- `validAt`

External reply supplies `requiredOperation: THREAD_REPLY` and uses the same server-generated reply timestamp for `validAt`, message creation, thread activity/attention, and minimized reply audit evidence.

The guard is a transaction precondition, not an AccessGrant update.

## Atomic store requirement

Before publishing staged reply state, the store must prove against authoritative AccessGrant state that:

- the grant exists in the guarded deployment;
- the grant still belongs to the guarded thread;
- the authoritative version equals `expectedVersion`;
- the grant is not revoked;
- the required operation remains present;
- `validAt` is a valid timestamp at or after issuance and strictly before expiry.

The in-memory adapter evaluates this guard before publishing any cloned state. Failure raises the provider-neutral authority-changed condition, which the external reply application path collapses to the existing conservative external-access denial.

The existing `expectedThreadVersion` condition remains separate and is still enforced. Release 0.10 therefore guards two independently versioned authorities at reply commit:

1. thread lifecycle/activity authority;
2. AccessGrant reply authority.

## Concurrent revocation regression

A deterministic integration regression advances only the AccessGrant from active version N to revoked version N+1 after initial reply validation and immediately before the reply commit. It deliberately does not change the thread version.

The expected result is:

- reply fails closed;
- the authoritative revocation remains version N+1;
- thread state/version/activity/attention receive no reply-caused change;
- no reply message is appended;
- no reply audit event is appended.

This proves the AccessGrant guard independently of the existing stale-thread guard.

## Expiry crossing regression

A deterministic sequence clock makes initial reply validation occur immediately before grant expiry and establishes the authoritative reply timestamp exactly at expiry.

The expected result is:

- the final authority guard rejects the reply at the expiry boundary;
- the grant itself remains otherwise unchanged;
- no thread activity/attention change occurs;
- no reply message or reply audit evidence is published.

## Preserved Release 0.10 semantics

This correction does not change:

- independent `THREAD_READ`, `ATTACHMENT_READ`, and `THREAD_REPLY` authority;
- reply lifecycle: allowed only in `NEW`, `IN_PROGRESS`, `AWAITING_EXTERNAL`, and `AWAITING_STAFF`;
- denial in `COMPLETED`, `EXPIRED`, and `DISPOSED`;
- authoritative `externalParticipantRef` attribution;
- immutable `EXTERNAL_TO_STAFF` messages;
- no automatic lifecycle transition;
- external activity/attention semantics;
- minimized `MESSAGE_APPENDED` evidence;
- existing stale-thread optimistic concurrency;
- separation of opened, downloaded, transferred/filed, and completed evidence.

## Scope and cost

No browser reply route or UI, AWS service, SDK, database implementation, production infrastructure, customer data, PHI, new dependency, or paid service is introduced by this correction.

Expected new recurring cost remains **$0**.
