# Release 0.12 — Production Delivery Boundary & Credential Bootstrap Design

## Purpose

Release 0.12 defines the production trust, credential-bootstrap, browser-session, abuse-control, notification, logging, recovery, and provider-adapter boundaries required before the synthetic external AccessGrant browser capabilities from Releases 0.7–0.11 can become a later real external-participant delivery system.

This is an **architecture/security design release only**. It creates no public production endpoint, live email, customer resource, production session, cloud adapter, PHI/customer data path, or compliance claim.

## Production bootstrap decision

The reference production design uses:

**non-secret bootstrap locator in the notification URL -> user-entered one-time proof -> atomic challenge consumption + new browser session -> clean session URL**.

A usable bootstrap credential is **not placed in the URL**. The raw AccessGrant bearer and production browser session bearer also remain out of URLs.

The URL locator is opaque/high entropy but is not sufficient authority and may be safely prefetched without consuming the challenge.

### One-time proof

Reference properties:

- cryptographically random;
- at least 50 bits effective entropy;
- at most 15 minutes lifetime;
- one successful use only;
- five failed attempts per challenge before lock/invalidation;
- raw proof never persisted;
- keyed/non-reversible verifier separated from the state store;
- successful consume + session creation atomic;
- reissue invalidates prior challenges.

### Pre-session BootstrapFormGuard

The bootstrap proof POST is state-changing because it can consume a challenge and establish the external browser session. No session exists yet, so a session-bound CSRF token is **not** a bootstrap prerequisite.

The reference pre-session request-integrity mechanism is a provider-neutral stateless **`BootstrapFormGuard`** rendered on the bootstrap GET page. It is server-authenticated and bound to:

- the intended `bootstrapId`/challenge;
- the current authoritative challenge version or equivalent replay generation;
- the exact expected Secure Exchange origin;
- a fresh unpredictable per-render nonce;
- an expiry of at most 10 minutes and no later than the underlying bootstrap challenge expiry.

The bootstrap proof POST must be non-GET, pass exact expected Origin validation, require same-origin Fetch Metadata when present, and carry a valid unexpired guard bound to the same current challenge version before the one-time bootstrap proof is evaluated.

GET does not consume, lock, advance, or authorize the challenge and does not establish a session. Rendering the stateless guard does not mutate authoritative challenge/application state.

Each proof attempt that reaches authoritative challenge processing conditionally advances or consumes the challenge version/generation, making the submitted guard stale for replay. If a failed proof remains retry-eligible, a fresh guard is required for the new version. Successful challenge consumption and fresh browser-session creation remain atomic.

`BootstrapFormGuard` is request-integrity material only. It is **not** an AccessGrant, one-time bootstrap authorization proof, browser session, application authorization, or wildcard capability. It cannot retrieve/read/reply/download and cannot make `bootstrapId` authoritative.

## Verification assurance

Two modes are explicitly distinguished:

- `MAILBOX_ONLY` — locator and proof may both arrive through the same email mailbox. This is **not MFA**. It mitigates URL-secret leakage/prefetch but not mailbox compromise or complete-message forwarding.
- `INDEPENDENT_CHALLENGE` — proof is delivered/established through a separately controlled channel/process. This is the required architecture when a customer/deployment policy requires protection against compromised-mailbox access.

Release 0.12 chooses no SMS, voice, IdP, email, or other verification vendor.

## Alternatives considered

### Magic link with high-entropy one-time URL secret

Rejected for the reference production architecture. Short expiry, one-time exchange, clean redirect, `Referrer-Policy`, and no-store reduce but do not remove risk from browser history, forwarding/screenshots, email link scanners/expanders, reputation systems, proxy/access logs, and accidental reuse as durable browser authority.

### Email link plus independently delivered code

Recommended when higher assurance is required, provided the code really originates from a separately controlled channel/process. Two steps from the same mailbox are not two factors.

### Email link plus known attribute

Rejected as primary proof because known attributes tend to be low entropy, discoverable, normalization-sensitive, and privacy-expanding.

### Email link plus same-email temporary code

Allowed only as `MAILBOX_ONLY`. It provides operational value by keeping active proof out of the URL and preventing GET prefetch from consuming access, but it does not mitigate mailbox compromise.

### Persistent external account/login

Deferred. Enrollment, recovery, MFA/passkey policy, credential stuffing, dormant-account retention, identity administration, and support are disproportionate to the initial short-lived thread-scoped exchange model.

## Browser session contract

Reference production cookie:

- `__Host-sx_external`
- host-only/no `Domain`
- `Secure`
- `HttpOnly`
- `SameSite=Lax`
- `Path=/`

The browser receives a new 256-bit random session bearer after successful bootstrap. The raw bearer is never persisted. The state store retains only a one-way verifier plus bounded opaque session/deployment/thread/grant/lifetime/revocation/version metadata.

Reference lifetime:

- 20-minute absolute maximum;
- 10-minute idle maximum;
- no silent/sliding absolute renewal;
- rebootstrap/reissue required after expiry.

One active browser session per AccessGrant is the reference rule. A new session invalidates the previous session for that grant.

Logout revokes the server-side session before cookie deletion. AccessGrant expiry/revocation and current application authorization continue to win over still-present browser state.

## Authorization invariant

The bootstrap locator, `BootstrapFormGuard`, one-time bootstrap proof, and browser session are delivery/request-integrity mechanisms only. None becomes product authorization truth.

Every protected request still revalidates the authoritative:

- deployment;
- thread;
- AccessGrant identity and proof boundary;
- explicit operation (`THREAD_READ`, `ATTACHMENT_READ`, `THREAD_REPLY`);
- revocation;
- expiry;
- lifecycle/resource state;
- expected resource/thread version where applicable;
- `AccessGrantAuthorityGuard` for external reply mutation.

No wildcard authority is added.

## Same-origin / CSRF decision

Production mutation protection does not rely on SameSite alone and is explicitly two-phase.

### Pre-session/bootstrap mutation

The bootstrap proof POST requires:

- POST/non-GET method;
- exact expected Origin validation;
- same-origin Fetch Metadata when present;
- valid unexpired `BootstrapFormGuard` bound to the intended challenge and its current authoritative version/generation;
- independent validation of the one-time bootstrap proof and current AccessGrant eligibility before session creation.

An established browser session or session-bound CSRF proof is not required because this POST creates that session.

### Post-bootstrap/established-session mutation

After successful bootstrap, every browser mutation requires:

- non-GET method;
- exact Origin validation;
- same-origin Fetch Metadata when present;
- session-bound CSRF/synchronizer proof;
- current external browser session validation;
- current AccessGrant/application authorization.

Neither CSRF/request-integrity mechanism grants application authority. CORS remains closed by default. `SameSite` remains defense in depth. CSP/form-action/frame/base-uri, no-referrer, no-store, and `nosniff` controls remain conservative.

## Email-scanner and prefetch handling

GET of the locator URL does not consume, lock, or advance a challenge and cannot establish or authorize a session. Automated link checks may fetch the page without establishing access.

The GET may render the stateless `BootstrapFormGuard` for the current challenge version, but that guard is not bootstrap authorization and cannot be used to retrieve content by itself.

Only an explicit proof POST that passes the pre-session request-integrity checks can attempt to consume/update the challenge, and successful exchange redirects to a fixed URL without locator/proof/guard material.

`MAILBOX_ONLY` does not claim protection from a scanner or compromised mailbox that can read both the locator and the same-email code and actively submit them.

## Abuse-control boundary

The application must enforce bounded request/body/file/message sizes, per-bootstrap failure limits, per-session/grant reply/download quotas, reissue/notification throttles, generic anti-enumeration errors, and authority checks before expensive storage/scanning work.

Reference starting limits documented for later validation include:

- bootstrap proof POST: 10/source IP/10 minutes;
- five failures/bootstrap challenge;
- reissue: 3/grant/hour plus deployment ceiling;
- reply: 10/session/10 minutes;
- attachment retrieval: 30/session/10 minutes.

Provider/edge controls such as Cloudflare rate/bot features may supplement these controls but remain replaceable and are not application authorization truth. Release 0.12 provisions none.

## Notification architecture

A provider-neutral notification contract covers semantic intents such as initial invitation, new-message notice, expiry/reissue notice, and revocation notice.

Ordinary notification content must not contain PHI, message/attachment content, raw AccessGrant bearer, browser session bearer/verifier, `BootstrapFormGuard`, session CSRF secrets, provider credentials, or unrestricted audit details.

The invitation URL may contain only the non-secret locator. A same-email one-time proof is permitted only for explicitly mailbox-only assurance; independent-challenge proof is not copied into the email.

No notification vendor is selected by this release.

## Logging and monitoring

Never log raw bootstrap proof, `BootstrapFormGuard`, raw AccessGrant bearer, browser session bearer, persisted verifier, Cookie contents, session CSRF tokens, reply/message bodies, attachment contents, unrestricted external contact information, provider credentials, or private keys.

Bounded opaque IDs and reason codes may support security telemetry for bootstrap failures/lockouts, session establishment/invalidation, grant revocation, compromise reissue, unusual download/reply attempts, throttling, notification failure, and adapter failure.

Application workflow audit remains distinct from operational/security telemetry.

## Production adapter boundaries

Future provider adapters must satisfy existing provider-neutral contracts for:

- authoritative state and transactional bootstrap/session/grant semantics;
- private protected object storage and content-integrity/lifecycle controls;
- authenticated fail-closed malware scanning/quarantine;
- customer-owned key/secret management, including keyed bootstrap-verifier and `BootstrapFormGuard` authentication key material;
- minimized notification delivery;
- logging/telemetry with sensitive-field exclusion;
- recovery that does not resurrect revoked authority.

No AWS service is selected merely by this release. Existing AWS-first references remain references behind ports rather than product semantics.

## Backup/recovery boundary

Production recovery must invalidate outstanding bootstrap challenges and browser sessions when monotonic continuity cannot be proven and must not silently restore a revoked AccessGrant to usability.

A deployment whose persistence technology cannot guarantee monotonic revocation across restore must support an access/security epoch or equivalent kill switch capable of invalidating pre-restore grants/sessions before access resumes.

## Customer-owned deployment boundary

The preferred model remains one isolated customer-owned deployment per customer.

Customers own production runtime/data accounts, domain/TLS, state/object storage, keys/secrets, verifier key material, notification sender/provider credentials, logs/backups, and customer-specific external-verification/retention policy.

LDW administers only through named role-based access granted by the customer. No shared customer credential or cross-customer shared master secret is required.
