# Release 0.8 — External Attachment Retrieval Core Prototype

## Scope

Release 0.8 extends the provider-neutral AccessGrant prototype with explicit `ATTACHMENT_READ` and an application-layer external attachment retrieval service. It introduces no public browser/API delivery surface and no production infrastructure.

## Authority separation

- `THREAD_READ` authorizes external conversation projection only.
- `ATTACHMENT_READ` authorizes eligible attachment retrieval only.
- Mixed grants may carry both operations, but each is checked independently.
- Current AccessGrant policy must explicitly allow every requested operation.
- Staff retrieval continues to require current staff authorization, queue scope, and staff `ATTACHMENT_READ` permission.

## Shared authoritative safety path

Staff and external retrieval now converge after authorization on one shared application primitive. That path verifies authoritative message scope; attachment deployment, thread, and message ownership; exactly `CLEAN` state and no deletion marker; protected-content availability; and byte-length equality with authoritative metadata. Only after those checks pass may `ATTACHMENT_DOWNLOADED` be committed.

External failures are intentionally collapsed to the conservative external access-denied result. The external retrieval result exposes only the derived safe-download filename, normalized media type, byte length, and byte payload needed by a future HTTP delivery adapter. Protected-content references and provider implementation details remain internal.

## Evidence

Successful external download records `ATTACHMENT_DOWNLOADED` with bounded opaque external actor, grant, thread, and attachment attribution. Raw bearer secret, verifier, file bytes, content reference, unrestricted original filename, and message body are not audit fields.

The evidence invariant remains:

`Opened != Downloaded != Transferred/Filed != Completed`

External download does not create TransferAttestation and does not complete or otherwise transition the thread.

## Deferred browser-delivery boundary

Release 0.8 intentionally has no public grant URL, email link, capability cookie, public attachment HTTP endpoint, production authentication, or external reply. Release 0.9 should separately review bearer delivery, browser/session behavior, response headers, caching, replay controls, and related HTTP trust-boundary decisions.

## Cost and dependencies

No dependency is added. No production service or infrastructure is provisioned. New recurring cost is **$0**.
