# Release 0.6 — Attachment Safety Core Prototype

## Status

Release 0.6 is a synthetic/local provider-neutral attachment-safety prototype. It does not expose production file transfer or provision infrastructure.

## Implemented

- provider-neutral Attachment metadata with `PENDING_UPLOAD`, `QUARANTINED`, `CLEAN`, `REJECTED`, and `DELETED` states;
- bounded per-deployment declared-metadata file policy;
- untrusted original filename plus separately derived safe-download filename;
- opaque attachment/content references generated server-side;
- provider-neutral `ProtectedContentStore` and process-memory synthetic adapter;
- application-only ingestion that validates authoritative thread/message ownership and publishes staged content as `QUARANTINED`;
- normalized trusted SYSTEM scan-result boundary for clean, malicious, and indeterminate outcomes;
- versioned/replay-safe scan transitions;
- one staff permission, `ATTACHMENT_READ`, used with live deployment/thread/queue authorization;
- authoritative attachment retrieval requiring exactly `CLEAN` before protected-content access;
- retrieval result containing safe filename, normalized content type, byte length, and synthetic bytes without a public URL;
- `ATTACHMENT_DOWNLOADED` emitted only after protected content successfully resolves and its audit commit succeeds;
- removal of the standalone synthetic download-evidence service/permission;
- staged-content cleanup compensation if metadata publication fails;
- deterministic failure tests for metadata/content transaction boundaries.

## State and scan semantics

Current application ingestion stages synthetic bytes and publishes `QUARANTINED`; it never marks new content `CLEAN`. `PENDING_UPLOAD` remains an approved domain state for a later real staging/upload adapter but is not a browser-driven flow in this release.

`QUARANTINED + CLEAN -> CLEAN`.

`QUARANTINED + MALICIOUS -> REJECTED`.

`QUARANTINED + INDETERMINATE -> QUARANTINED` with a versioned normalized scan record.

Only `CLEAN` is normally retrievable. `PENDING_UPLOAD`, `QUARANTINED`, `REJECTED`, `DELETED`, unknown, invalid, or deleted-marked attachments fail closed. Exact replay of the same normalized scan-result reference/outcome is idempotent; conflicting replay or new scan transitions from non-quarantined states fail.

## Declared metadata limitation

Allowed extension, MIME type, and media category are bounded policy inputs. They remain caller-declared metadata and are **not** authoritative content-signature/type verification. Production arbitrary upload requires a later authoritative content classification/type verification gate; no large parser/file-identification dependency is introduced in 0.6.

## Download evidence invariant

Normal application download evidence now exists only inside `AttachmentService.retrieveStaffAttachment()` after:

1. actor deployment matches;
2. authoritative thread is resolved;
3. live STAFF authorization includes current queue scope and `ATTACHMENT_READ`;
4. authoritative message is resolved;
5. attachment deployment/thread/message association matches;
6. attachment state is exactly `CLEAN` and not deleted;
7. protected content exists, resolves successfully, and matches the recorded byte length.

Only then is `ATTACHMENT_DOWNLOADED` committed. The retrieval result is returned only if that audit commit succeeds. Authorization/state/content failures emit no successful download event.

Download remains distinct from Opened, TransferAttestation, lifecycle transition, and completion.

## Failure/compensation boundary

Protected content and workflow metadata deliberately do not pretend to share a distributed transaction. Ingestion stages content first and then publishes metadata/audit using the existing atomic WorkflowStore commit. If publication fails, the service attempts deletion of the staged content. Failure to confirm that cleanup is surfaced explicitly rather than hidden.

Scan attachment state and its minimized audit events commit atomically within WorkflowStore. Retrieval content failure occurs before download audit. The prototype therefore proves the key ordering/compensation semantics without selecting an AWS-specific mechanism.

## Browser boundary

No arbitrary browser upload route or attachment download route was added. The Release 0.5 Synthetic Development Demo remains unchanged. Browser delivery can be considered in a later release after the application core is reviewed.

## Non-goals retained

No production authentication, Cognito, production sessions, AccessGrant, external secure retrieval/reply, email, real malware scanner, GuardDuty, S3, KMS, DynamoDB, SES, API Gateway/Lambda, AWS SDK, infrastructure as code, Cloudflare/AWS production deployment, customer data, PHI, inline preview, OCR, document parsing, archive extraction, AI processing, analytics, or paid service is introduced.

## Cost and dependencies

New recurring cost: **$0**.

No runtime or development dependency version is added or changed. Package metadata advances from `0.5.0` to `0.6.0` only.
