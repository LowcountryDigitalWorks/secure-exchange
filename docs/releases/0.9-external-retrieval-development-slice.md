# Release 0.9 — External Retrieval Development Slice

## Scope

Release 0.9 adds the first server-rendered browser delivery adapter over the merged provider-neutral AccessGrant, external conversation, and external attachment retrieval services. It is a disabled-by-default **Synthetic Development Demo**, not a production public portal, finalized credential-delivery design, or customer deployment.

## Development gate and namespace

The existing `SECURE_EXCHANGE_SYNTHETIC_DEMO=enabled` gate must be enabled, and the external retrieval slice additionally requires `DEMO_EXTERNAL_RETRIEVAL_ENABLED=enabled`. The route namespace is `/demo/external/access`. With the second flag disabled, those routes are not registered.

## Credential POST and browser capability

The initial page accepts thread reference, grant reference, and bearer secret by same-origin POST. Deployment context remains server-side. No raw AccessGrant secret is placed in a path, query, fragment, redirect target, generated hyperlink, hidden field after establishment, localStorage, sessionStorage, IndexedDB, audit, analytics, or application logs.

Successful presentation sets one host-only HttpOnly SameSite=Strict capability cookie scoped to `/demo/external/access`, with `Max-Age=600` and `Secure` on HTTPS. No Domain attribute or persisted verifier is stored. The cookie is a transport prototype only: authoritative AccessGrant expiration/revocation/thread eligibility and explicit per-operation checks are revalidated on every protected use.

## Conversation and attachment operation independence

`THREAD_READ` alone can render only the existing bounded external conversation projection. `ATTACHMENT_READ` alone can list bounded clean attachment candidates and perform authoritative downloads. Mixed grants may do both independently. The adapter never broadens the grant to simplify page rendering.

Candidate metadata contains only safe-download filename, normalized media type, bounded byte size, and opaque message/attachment selectors required for the later POST. It excludes original untrusted filename, protected-content reference, scanner/provider internals, staff/queue data, audit, and grant metadata.

## Download HTTP posture

Download is same-origin POST and delegates directly to `ExternalAttachmentRetrievalService`. The response is attachment-only and uses defensive `Content-Disposition` with `safeDownloadFilename`, normalized media type, exact content length, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store, private`, `Referrer-Policy: no-referrer`, and `Cross-Origin-Resource-Policy: same-origin`.

The existing application path remains authoritative for AccessGrant validation, explicit `ATTACHMENT_READ`, current thread eligibility, authoritative ownership, exactly `CLEAN`, protected content, byte-length integrity, and `ATTACHMENT_DOWNLOADED`. Download remains distinct from TransferAttestation and completion.

## Validation gate

Release readiness requires the repository-controlled `npm run validate` gate and the protected-main pull-request-context `validate` check. Browser coverage exercises both desktop and mobile Chromium while preserving the disabled-by-default production posture.

## Deferred production decisions

Email-link/bootstrap credential delivery, production identity/session design, anonymous abuse/rate controls, production public deployment, notification delivery, browser upload, external reply/`THREAD_REPLY`, production storage/scanner adapters, infrastructure, and operational monitoring remain separately gated. The synthetic cookie design is not approval for Internet exposure.

## Dependencies and cost

No runtime or development dependency is added. New recurring cost is **$0**.
